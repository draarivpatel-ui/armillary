# Armillary privacy

Version 0.1.0. Every statement below names where it comes from. Where something was not verified, it says so.

The short version: Armillary reads the history your AI agents already keep on your Mac, copies it into one archive file on your Mac, and shows it to you. The app itself makes no network requests and has no telemetry or analytics. Nothing is read until you say yes on the first-run screen.

## What it reads

Nothing is read before you consent. On a fresh install the app opens its own archive file and shows the first-run consent plaque; discovery, the file watcher, the live detector and the first import start only after consent is recorded (`app/src-tauri/src/main.rs`, `launch.rs`, `firstrun.rs`: `scan_if_consented` refuses with "consent not recorded"). Choosing "Not now" records the decline and withdraws any earlier consent (`firstrun.rs`, `record_consent_in`). On a fresh install the archive is then empty. If you choose "Not now" later, for example on a Replay, the sessions imported before stay in the archive and the Almanac, Folio and Search still show them; only Delete archive and reset (below) removes them. The plaque says so above its buttons.

The check is in the core, not only in the screens. Every command that reads agent folders or the process table (the agent list, the Switchboard's config scan, the live list, Import now, and the Launchpad's program lookup) checks the consent file first and answers `consent_required` without touching anything when consent is missing (`archive_api.rs`, `consent::require`; one test per command proves that after a decline nothing under a fake home folder is read). After "Not now" the Orrery, Field Guide, Switchboard and Launchpad say "Armillary has not been given access" and offer a Give access button that shows the plaque again. Choosing "Not now", declining later (also on a Replay), or choosing Delete archive and reset stops the file watcher, the live detector and any import (`launch.rs`, `stop_background_services`): a running live-detector pass and an import that is about to start (including while discovering targets) stop immediately (`live.rs`, `scan_until` and `maybe_emit_if_changed_until`; `archive_api.rs`, `import_now_in`; `firstrun.rs`, `firstrun_scan`; `launch.rs`, `start_background_services`); a watcher that saw a file change just before is stopped during its short wait and starts no import; a file already being read finishes and nothing new is read, and the import goes on to no other source or agent (`importer.rs`, `spawn_watcher_with_ignores` and `cancel_running_imports`; `crates/adapters/src/boundary.rs`, `with_read_stop`). If the app quits during the first run, after you consented but before it finished, the next launch starts nothing and the plaque asks again (`consent::services_allowed_at_launch`).

After consent, the plaque tells you it reads (`ui/firstrun/src/host/ConsentPlaque.tsx`):

- Session histories your agents already keep.
- Agent settings, rules and MCP config files.
- Which agents are installed (it checks for their apps and commands).
- Running agent processes, for the live Orrery.

It looks only in the folders each agent keeps on this Mac, as listed in Armillary's catalogue (80 built-in entries; the plaque names the 76 that keep a data folder on macOS). The plaque shows them; the per-agent folders are in `crates/adapters/src/builtins/*.toml`. Of the 80, 22 have a history importer (see README.md); the rest are detected or have their config shown, not imported.

How it reads, from SPEC.md section 5 and the adapter tests:

- Reading is read-only. Armillary never modifies an agent's files. The Switchboard (settings view) is read-only in v0.1: `config_scan.rs` contains no code that writes files outside its own tests.
- Every source uses an approved root and one filesystem read boundary: canonical containment, a refusal list for credential-looking files, no-follow opens that stop a symlink from escaping to a file such as `../auth.json`, regular files only, byte and record limits.
- The Switchboard's reads (settings, rules and MCP config files) go through the same boundary (`config_scan.rs`, `guarded_read`). The approved root is the agent's own config folder for a global file and the project folder for a project file. A link that stays inside that folder is read; a link that leads out of it is not opened and is shown as "a link that leads outside its folder". A file that sits directly in your home folder (such as `~/.claude.json`) is never read through a link. This also means a global rules or settings file that is a link into a folder elsewhere, such as `~/.claude/CLAUDE.md` pointing into a dotfiles repository, is not opened and is shown as a link that leads outside its folder. A project folder may have any name (one called `keychain-app` is read normally); a project that sits inside `.ssh`, `.aws`, `.gnupg` or a similar credential folder is refused, and so is a credential file inside a project. When a settings file cannot be parsed, the Switchboard shows only "could not parse <file>", never the parser's message, because that message can quote the file.
- The live detector never opens a file reached through a link in an agent history folder (`live.rs`, `open_history_file`). Its folder listing can follow a linked folder far enough to see the names and sizes inside, but those files fail the containment check and nothing in them is opened.
- **Size limit.** Each history file, and each SQLite database or write-ahead log, is read whole and is skipped if it is larger than 64 MiB (`crates/adapters/src/boundary.rs`, `MAX_SOURCE_BYTES`) or holds more than 250,000 records or rows (`MAX_SOURCE_RECORDS`). This holds for every history importer, including the ones for Roo Code, Kilo Code, Cline, Continue and Cursor CLI (`crates/adapters/src/modules/mod.rs`, `report_size_refusals`). The Field Guide shows "Skipped, too large (over 64 MiB)" or "Skipped, too large (over 250,000 records)" with the file's name: when you open it, for the files the latest import skipped, and as they happen while it is open during an import. The archive keeps one notice per file; it goes away when the file imports again or is no longer there. Roo Code, Kilo Code and Cline keep one conversation in several files: when only the conversation file is too large, the task can still appear with the fewer messages its other files hold. A Switchboard settings or rules file is read only up to 1 MiB.
- SQLite histories are copied through that boundary (database plus its write-ahead log) into a private temporary snapshot and queried there. The source database is never opened for writing.
- Detection is passive: it looks for files and commands and does not launch agent programs. An explicit version probe exists in `crates/adapters/src/probe.rs` (trusted exact path, 5 second cap, output cap) but discovery never calls it, and the app does not call it today (a search of the app code found no caller).
- The live view reads the process table (command name, working folder, start time) using the `sysinfo` library, and watches history files for activity. You can turn the process scan off by starting the app with the environment variable `ARMILLARY_PROCESS_SCAN=off` (`app/src-tauri/src/live.rs`).

## What it never opens

- Credential files, keys and tokens. The plaque promises it ("Opens credential files, keys or tokens" is on its Never list). The code refuses `auth.json`, `credentials.json`, `.credentials.json`, `credentials`, `.env` and `.env.*`, any file ending in `.key` or with "keychain" in its name, `id_rsa*`, `id_ed25519*`, `id_ecdsa*` and `id_dsa*`, `.netrc`, `.pgpass`, `.git-credentials`, `.npmrc`, `.pypirc`, the GitHub CLI's `gh/hosts.yml`, and anything inside `.ssh`, `.aws`, `.gnupg`, `credentials` or `Keychains` (`crates/adapters/src/credentials.rs`). The check runs on the name you see and on the real location a link resolves to. Inside an agent's history folder, folder names are checked only against those credential folders, because history folders are named after projects: Claude Code keeps a project called `keychain-app` in a folder with "keychain" in its name, and that history is imported and shown live (`boundary.rs`, `refuse`; `live.rs`, `credential_path`). This is a name-based list plus the symlink-safe read boundary above. It is not a scanner for secrets inside ordinary files: see "Things to know" below.
- Anything outside the approved agent folders.

## What it stores, and where

- One archive file, `armillary-archive.sqlite3`, in the application's data folder (`archive_api.rs`, `open_archive_in`). The folder is Tauri's per-app data folder for the identifier `com.armillary.app`; on macOS that is normally `~/Library/Application Support/com.armillary.app` (this location follows Tauri's convention and was not re-checked on a real install today).
- The archive holds the sessions it imported: prompts, replies, tool calls and results, file names touched, token usage, project folders, times. It is a full copy of what the importer read, so treat it as sensitive as the originals.
- Permissions: the archive file is created with owner-only access (mode 0600) and opened without following symlinks (`crates/archive/src/archive.rs`). SPEC.md section 4 says private archive and snapshot permissions are enforced and tested.
- The archive is a plain SQLite file. No encryption is described in the SPEC and none is in the code (the SQLite library is bundled, with no encryption extension).
- A small consent file, `firstrun.json`, in the same folder (mode 0600, written atomically): whether you consented, when, whether the first run finished.
- Two settings are kept in the app's web storage (local storage), outside that folder: the theme and the Launchpad's recent launches (agent and project folder names).
- **The archive keeps its copy.** When an agent deletes or prunes one of its own transcripts, Armillary does not mirror that: the archive keeps its copy of the transcript until you delete the archive (SPEC.md section 4: missing files "never imply deletion"). 0.1.0 has no way to delete a single session from the app.

## Removing your data

- **In the app:** the rail has **Delete archive and reset**. After you confirm, it stops the watcher, the live detector and any import (a running live-detector pass and an import that is about to start stop immediately; a file already being read finishes and nothing new is read), closes the archive, deletes `armillary-archive.sqlite3` with its `-wal` and `-shm` files and any copies that "Move it aside" kept (`armillary-archive.sqlite3.bak-<time>`, with their `-wal` and `-shm`), deletes `firstrun.json`, removes leftover import snapshot folders from the system's temporary folder, clears the app's local storage (theme and recent launches) and shows the first-run plaque again. A new, empty archive file is created in place of the old one so the app keeps working. Your agents' own files are not touched. If the archive was emptied but a later file could not be removed, the dialog says "Partly deleted" and names it; the background watcher and live detector stay stopped until Armillary is opened again. (`launch.rs`, `archive_delete`; `archive_api.rs`, `delete_data_in`; `crates/archive/src/archive.rs`, `reset_to_empty`.)
- **By hand:** quit Armillary and delete the folder `~/Library/Application Support/com.armillary.app` (the bundle identifier is `com.armillary.app`, from `app/src-tauri/tauri.conf.json`). macOS may also keep the web view's storage and caches in folders named after the same identifier, such as `~/Library/WebKit/com.armillary.app` and `~/Library/Caches/com.armillary.app`; these paths follow macOS conventions and were not checked on a real install.
- Deleting the file removes it from the folder; like any deleted file, its old blocks may remain on the disk until they are reused. FileVault (macOS disk encryption) protects them at rest.
- **If the archive cannot be opened**, the app says why (damaged, made by a newer version, or another reason such as the file being in use or not readable, named as it is) and opens on an empty, temporary archive. Nothing is deleted: the button "Move it aside and start fresh" renames the old file to `armillary-archive.sqlite3.bak-<time>` next to the new one, and is refused while the archive opens normally. That copy holds your full history until you delete it by hand or use Delete archive and reset.

## What is never sent

The app makes no network requests of its own. This is what supports that, and what does not:

- The app's release Content Security Policy in `app/src-tauri/tauri.conf.json` (`app.security.csp`) is `default-src 'self'; script-src 'self'; style-src 'self'; style-src-elem 'self' 'unsafe-inline'; style-src-attr 'none'; img-src 'self' data: blob:; font-src 'self'; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; frame-src 'none'; form-action 'none'; worker-src 'none'`. Connections are allowed only to the app's own inter-process channel (`connect-src ipc: http://ipc.localhost`). Scripts and fonts load only from the app itself (`'self'`); images load from `'self'`, `data:` and `blob:` URLs; style sheets default to `'self'` (`style-src 'self'`), inline `<style>` elements are allowed (`style-src-elem 'self' 'unsafe-inline'`, used by the terminal library), and inline `style` attributes are blocked (`style-src-attr 'none'`). `object-src`, `base-uri`, `frame-src`, `form-action` and `worker-src` are `'none'`. (In development builds only, `devCsp` allows `'unsafe-inline'` for `script-src` and `style-src` and connections to the local dev server at `http://localhost:5173` and `ws://localhost:5173`.) The release policy was validated in the built app with a violation reporter.
- No HTTP client library is among the direct dependencies of the app or its crates (checked in each `Cargo.toml`; the app's framework, Tauri, has its own dependencies that were not audited here), and a search of the app and UI source found no `fetch`, `XMLHttpRequest`, `WebSocket` or beacon calls. The app has no updater and no plugins (`capabilities/default.json` lists only event listening and the app's own commands).
- No telemetry and no analytics: none in the code, and none is described anywhere in the sources.
- Tracing is off by default. With `ARMILLARY_TRACE_IPC=1` the app prints lines to the terminal's standard error that carry command names, ok or error codes and counts, never session content, titles or paths (`archive_api.rs`, `trace`). With `ARMILLARY_FPS_LOG=1` it prints frame-rate lines for the first-run animation, and if that variable is set to a file path it also appends them to that file (`firstrun.rs`, `fps_report_line`). Both switches are developer settings that are off unless you set them; neither sends anything anywhere.
- Imported Markdown, links, attachments, tool output and search snippets are treated as untrusted: escaped, with remote fetches disabled (SPEC.md section 6).

Two honest exceptions to "nothing touches the network":

1. The Field Guide has a "Docs" link for each agent (a web address from the built-in catalogue). The app does not load these addresses. They are ordinary links, and a click is the only way one could leave the app. How macOS handles that click (whether it opens your browser) was not tested for this document.
2. The Launchpad starts an agent (or a plain shell) inside a terminal in the app. That program is yours and runs under its own network behaviour; Armillary's "no network" promise covers Armillary, not the agents you start from it.

The release build was also checked for dev-only leftovers: the sample snapshot and the sample-data bridge exist only in presentation builds, and the release script fails if a dev-only binary is in the bundle (`tools/build-release.sh`). It also clears the export, presentation and capture build flags and fails if the built interface has any of them on (`tools/check-release-flags.sh`).

## Things to know

- **Secrets inside ordinary files.** The credential refusal is by file name and by safe reading. An agent transcript, a settings file or an MCP config can still contain a key or token that the user or agent typed into it. Armillary copies transcripts into the archive as it finds them. The Switchboard masks key-looking values in its previews and in each server's command, arguments and address: passwords in connection addresses and connection strings (`Password=` or `Pwd=` between semicolons, `user:password@host`), the value after `Authorization:`, `Bearer`, `Cookie:` or a header or flag named for a secret (`--token`, `--password`, `--auth`, `--pat`, `--key` and similar), the password after `-p` or `-pPASSWORD` (mysql, sshpass; npx package names and docker port maps after `-p` stay visible) and after the colon in `-u user:password` (curl), `KEY=value` inside a shell command, and token-like parts of a web address: path parts, query and `#fragment` values that look like keys, including hex tokens and UUIDs (`config_scan.rs`, `[masked]`). Short numbers and file paths after such a flag stay visible (`--max-tokens 4096`). That is not a guarantee: a secret in a shape it does not recognise is still shown, for example a short value under a neutral name (`?k=abc123`) or a plain word as a bare argument.
- **Export is planned, not in 0.1.0.** The Folio's export to Markdown or HTML, and its Redact pass, are switched off in this version because saving the file was not finished (the buttons wrote nothing). The code is kept behind a build switch that is off.
- **macOS only for v0.1.** Reading histories on Windows fails closed by design (SPEC.md section 5), and the first-run screen and consent plaque are macOS only.
- **Not externally audited.** Two internal safety reviews found consent, link, export and deletion problems, which this version fixes. No independent third-party audit has been done, so treat the privacy claims as claims backed by this repository's code and tests, and read the code if it matters to you.
- **Tested on synthetic data.** The built app was verified end to end on a temporary home folder holding a synthetic, invented dataset. It has not been exercised against a large set of real agent folders.
